Final Prompt for the Colitech Multi-Agent Research Assistant

Copy the text below into your coding agent while working in the Colitech/Adaptive Multi-Agent Research Assistant repository.

You are the implementation engineer for the Colitech Multi-Agent Research Assistant. Build a working, locally runnable, evidence-grounded research application. This prompt is the implementation instruction; the supplied Colitech graph image, node-interaction narrative, Adaptive Multi-Agent Research Assistant v2 runbook, and Mermaid diagrams are supporting references to consult when available. The older teaching prompts describe a small prototype and a separate Monk safety/evaluation/deployment exercise; use them for useful ideas, but do not replace the Colitech architecture with their earlier three-step graph, Bedrock-only configuration, or AWS infrastructure.

Start by inspecting the repository. Read the current package layout, graph wiring, schemas, tests, configuration, and README. State what already works and what is missing. Preserve working interfaces and code. If the references disagree with the repository, explain the difference and choose the smallest coherent migration. Work in verified milestones; after each milestone run the relevant tests and fix failures before moving on. Do the implementation rather than stopping at a plan.

Required product behavior

Accept a structured research request, plan it into sub-questions, route each sub-question to an eligible model, research permitted sources in parallel, validate every candidate fact against retrieved evidence, retry missing coverage within hard limits, and produce a cited report from validated facts only. Expose live progress in a small browser UI and a typed API. Persist enough state to retrieve a completed run and inspect its cost, route, validation, and outcome. A run with insufficient evidence must say so plainly; it must never fill gaps with fabricated facts or citations.

Use FastAPI, LangGraph, Pydantic v2, and Python. Prefer the repository's existing supported Python version; if setting up a new package, use Python 3.12 or newer. Keep api, graph, nodes, llm, storage, and tools separate under the existing package (the reference layout is src/aar). Use SQLite for local checkpoints, run records, telemetry, and routing preferences. Local document retrieval starts with an indexed keyword search and stable document/chunk citations; vector search and a hosted database are not required for this local MVP.

Exact execution boundary and graph

The API Gateway, Run Registry, and Run Service are application components outside LangGraph. The API validates the full request. Run Registry atomically creates a persistent queued run_id and uses it as thread_id. Run Service creates the initial state, invokes one compiled graph reused across requests, publishes progress, and records terminal success or failure. Do not compile a new graph for each request.

Inside LangGraph, implement this order:

START → Request Intake → Planner → Complexity Router → Research Supervisor → Send(Web Search Worker and/or Document Search Worker) → Research Join → Validator → Coverage Gate → Writer → Final QA → Learning Update → END

Coverage Gate may loop only to Research Supervisor. Planner runs once per run. Each source_hint=both creates two parallel Sends, one web and one documents; it is not a third worker. The summarizer is a shared utility invoked by workers when useful, even if the existing file is named summarizer_worker.py; do not register or dispatch it as an independent worker. Join all dispatched outputs before Validator. Learning Update is the last graph node. Optional user feedback happens after the run through the API and never restarts the graph.

Data and node contracts

- Define ResearchRequest with question, allowed_sources, desired_depth, risk_level, and max_cost_usd. Reject malformed or unsupported values before creating a run. Define typed SubQuestion, Fact, provenance, validation result, model attempt, progress event, and response schemas. Give each Fact a stable id, claim, exact evidence quote, source URL or stable document citation, source title, and sub-question id. Use graph-state reducers that safely merge parallel outputs; facts must merge by id so validation updates do not duplicate them.
- Request Intake checks required state, changes status to running, and emits an intake event without recreating the state.
- Planner creates 3–7 distinct, collectively useful sub-questions. Each has a valid source hint and a measurable coverage goal. Respect allowed_sources; validate structured model output. A bounded deterministic planning fallback may keep an offline run usable, but report when fallback was used.
- Complexity Router scores each sub-question independently on reasoning depth, context size, tool need, risk, and accuracy need, each from 0–5. Make the scoring rules explicit and deterministic. Map totals 0–4 to the cheap/simple tier, 5–10 to standard/moderate, and 11–25 to strong/complex. Route planning, each sub-question, and writing through route_planning(), route_one(), and route_writing() (or equivalent existing functions) using the same model policy. Select a model alias only after filtering for enabled status, provider availability, required capability, context capacity, required tier, premium policy, and remaining budget. Prefer the lowest projected cost among eligible aliases; use learned preference only to break same-tier ties. Record the score breakdown, selected tier, alias, and rejection reason. If none qualifies, record route_unavailable and use only an explicitly described deterministic fallback or limitation. Never silently change tiers. The selected alias must be the alias actually called.
- Research Supervisor dispatches only active or uncovered sub-questions. web sends one Web Worker, documents sends one Document Worker, and both sends one of each. Pass only the required worker packet. Enforce a cumulative maximum of four worker tool uses per sub-question across both workers and all rounds; count search, fetch, document retrieval, and summarization calls. Use bounded timeouts. Preserve successful results if another worker fails.
- Web Worker uses configured Tavily search or an explicitly labeled test fixture, validates every URL against SSRF risks, then fetches readable page text within time and size limits. Check redirects and resolved destinations as well as the original URL; reject loopback, private, link-local, and other disallowed destinations. Preserve the exact returned URL and fetched text in the current-run provenance ledger. Document Worker searches indexed local passages and preserves document id, chunk id, passage, and a stable citation. Both workers may call the shared summarizer, which must retain source identity and exact quotation context. Neither worker may create a fact from an unknown URL or absent passage. Missing keys, empty indexes, unsafe links, and tool failures produce warnings or uncovered work, never fake evidence in a live report. Fixtures and fake models are allowed in explicitly labeled tests/demos only.
- Research Join merges worker results and provenance safely, deduplicates equivalent records, and forwards all candidate facts to Validator. Validator is deterministic and calls no LLM. Accept a fact only when its reference belongs to this run, its nonempty quote occurs in that exact retrieved source after documented whitespace/case normalization, its claim overlaps at least two meaningful content words with its sub-question or coverage goal, and its normalized claim has not already been accepted. Save precise rejection reasons, including unknown source, missing quote, quote absent from source, irrelevant claim, and duplicate claim. Do not have Validator decide budget.
- Coverage Gate checks every sub-question's coverage goal and controls retry. Allow at most two total research rounds, counting the first; retry only uncovered sub-questions when a second round is available and budget permits. It never reruns Planner or skips Join/Validator. When coverage remains incomplete because of round, source, route, or budget limits, pass explicit limitations to Writer. A zero-budget run must make zero paid model calls.
- Writer has no search or retrieval tools and receives only validated facts, approved references, the question, and coverage limitations. Write a two- or three-sentence executive summary, a section per sub-question, inline numbered citations after supported claims, and a deduplicated Sources list of exact approved references. A deterministic template writer may provide a limited offline result; it must not create new facts or sources. Final QA deterministically verifies required sections, citation-to-fact mapping, unique and complete source listings, unknown links, rejected-claim leakage, and disclosure of incomplete coverage. If an LLM draft fails QA, return a non-approved status with specific warnings or replace it with a safe template report from validated facts; do not silently serve an unsupported draft as approved.
- Learning Update runs after Final QA. Persist per-alias exponential moving averages of validation/pass outcomes, cost, and latency with alpha = 0.3, plus a derived same-tier preference score. Learning must not override capability, tier, provider availability, budget, or safety rules. A learning-store failure must not erase an otherwise completed report.

Model, cost, security, and persistence rules

Provide a ModelClient.generate(...) interface and a registry that resolves alias → catalog entry → provider adapter. Support the reference provider families through adapters or clearly scoped existing integrations: Fake for tests, local Ollama, Gemini, Anthropic, OpenRouter, and Bedrock. Each adapter normalizes response text, actual token usage when available, latency, model alias, provider, finish reason, cost estimate, and a shared controlled error. A provider error must not crash the entire run. Keep vendor model IDs, capability flags, context limits, tier, and pricing in a reviewable catalog; check current official provider documentation before enabling a live paid model. Do not print, commit, or persist credentials. Read keys from the environment at the adapter boundary; settings and telemetry should expose only whether a key is present.

Enforce max_cost_usd before each paid model or metered research-tool call, not only after a run. Parallel workers must share an atomic budget reservation: reserve a conservative worst-case call cost using token and tool limits before dispatch, reject calls that cannot fit, and settle reservations against recorded usage afterward. Keep a hard maximum output-token limit. Record the difference between estimated and actual provider usage where available. Document any tool whose billing cannot be measured per call; do not claim a hard all-in ceiling that excludes it. Never silently spend above the enforced request ceiling. Record selected aliases and provider calls separately so tests can prove they match.

Keep checkpoints, Run Registry records, current-run provenance, telemetry, routing preferences, and the document index conceptually distinct. Telemetry should record run_id, timestamp, node, sub-question id where applicable, alias/provider/tier, token counts, estimated cost, latency, tool outcome, validation decision, QA result, and safe error code. Write telemetry from actual API, graph-node, worker, model, and validation paths, not just from isolated storage tests. Redact secret-shaped fields and omit raw prompts, answers, and full source content by default. Store user rating and optional notes in telemetry only.

API, UI, and progress

Implement these routes with typed responses and controlled errors:

- POST /api/research: accept the entire ResearchRequest, create a run, return HTTP 202 and run_id promptly.
- GET /api/runs/{run_id}: status, round, warnings, and spent/reserved cost.
- GET /api/report/{run_id}: final report, citations, limitations, QA status, and cost when available.
- GET /api/stream/{run_id}: Server-Sent Events for live progress and a terminal event.
- GET /api/models: catalog entries and current learning scores without secrets.
- GET /api/metrics/summary: run cost, calls by tier, validation pass rate, premium avoidance, and average latency.
- POST /api/runs/{run_id}/feedback: optional rating and note stored outside graph state.
- /health and /ready: application and dependency readiness.

Emit meaningful events such as run_started, plan_created, route_selected, worker_started, fact_candidate, fact_validated, coverage_decision, report_drafted, qa_completed, and run_completed or run_failed. Avoid leaking stack traces or secrets to clients. Provide a simple browser page with structured request controls, live Progress and Report panels, readable citations, run status, and error/limitation messages. Use the Colitech diagram as the visual reference; use an actual logo only if the repository contains one.

Verification and delivery

Implement and verify in this order: (1) schemas/state/configuration, (2) catalog and provider interface, (3) tools and deterministic validation, (4) compiled graph with controlled fake-provider tests, (5) real alias routing and budget enforcement, (6) telemetry and learning, (7) API/SSE/UI, (8) documentation and final checks. Use network-free fixtures and a recording fake provider for automated tests. Test at minimum:

- scoring boundaries 4/5/10/11; each alias rejection reason; selected alias equals invoked alias;
- parallel both dispatch, correct Join/reducers, and a selective second-round retry that never repeats covered sub-questions;
- unknown source, absent quote, irrelevant claim, and duplicate fact rejection; no invented citation in an approved report;
- zero paid calls at zero budget and no overspend under concurrent workers;
- actual telemetry rows from a compiled run, persisted run/report retrieval, SSE event order and terminal status, and post-run feedback isolation;
- learning changes only a same-tier tie-break, while a failed learning write leaves the report intact;
- a complete API run using no network or real key, plus one clearly labeled optional live-provider smoke test when configured.

Run the repository's required checks, including pytest, ruff, and mypy where configured. Fix failures caused by your changes and report the exact commands and outcomes. Deliver the working code, .env.example with placeholders only, a concise README/runbook with copyable local setup and sample question, updated diagrams when graph wiring changes, and a final gap report. Make clear which providers and source tools were genuinely exercised live, which used fixtures, and what remains unavailable because of missing configuration.

Separate follow-on work: The older Monk exercise suggests a Bedrock guardrail demo, LangSmith traces, a JSONL evaluation set with deterministic citation checks and planner/report graders, and AWS deployment. After the local Colitech MVP passes, give a short, separate plan for these optional additions. Do not hard-code the Monk service name, Bedrock-only model, RDS/pgvector requirement, or ECS settings into this MVP, and do not initiate paid cloud provisioning as part of this prompt.
